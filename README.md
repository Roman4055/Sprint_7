# Автотесты API сервиса «Яндекс.Самокат»

Учебный проект: автоматизация тестирования REST API учебного сервиса
самокатов (создание, авторизация и удаление курьеров; создание заказов,
принятие заказов, получение списка заказов и заказа по трек-номеру).

## Стек

- Python 3.13+
- pytest — фреймворк для запуска тестов
- requests — HTTP-клиент
- allure-pytest — генерация отчётов Allure
- Faker — генерация тестовых данных

## Хелперы (`helpers.py`)

- `create_courier(payload)` — создание курьера (POST);
- `login_courier(payload)` — авторизация курьера (POST);
- `create_and_login_courier(payload)` — создание + авторизация, возвращает `id`
  курьера (id приходит только в ответе на логин, а не на создание);
- `delete_courier(courier_id)` — удаление курьера (DELETE, id в пути);
- `create_order(payload)` — создание заказа (POST, возвращает `track`);
- `accept_order(order_id, courier_id)` — принятие заказа
  (PUT, номер заказа в пути, `courierId` в query-параметре);
- `accept_order_without_order_id(courier_id)` — запрос принятия заказа без номера;
- `get_order_by_track(track)` — получение заказа по трек-номеру (GET, параметр `t`).

## Описание тестов

### test_creating_courier.py — создание курьера (`POST /api/v1/courier`)
- курьера можно создать при передаче обязательных полей (201, `ok: true`);
- нельзя создать двух курьеров с одинаковым логином (409 + текст ошибки);
- нельзя создать курьера без логина / с пустой строкой в логине (400 + текст ошибки);
- нельзя создать курьера без пароля / с пустой строкой в пароле (400 + текст ошибки).

### test_login_courier.py — авторизация курьера (`POST /api/v1/courier/login`)
- успешная авторизация возвращает `id` курьера (200);
- пустая строка в логине/пароле — ошибка (400 + текст);
- отсутствие поля логина/пароля — ошибка (400 + текст);
- неверный логин/пароль и несуществующий пользователь — ошибка (404 + текст).

### test_del_courier.py — удаление курьера (`DELETE /api/v1/courier/:id`)
- успешное удаление существующего курьера (200, `ok: true`);
- запрос без ID в пути — ожидается ошибка (см. баг-репорты);
- запрос с несуществующим ID — ошибка 404 + текст (см. баг-репорты).

### test_order_creating.py — создание заказа (`POST /api/v1/orders`)
- параметризованные кейсы по полю `color`: один цвет, два цвета, без цвета;
- в ответе возвращается непустой `track` (201).

### test_order_list.py — список заказов (`GET /api/v1/orders`)
- позитивные кейсы (параметризованные): выдача без фильтров, фильтр по
  `courierId`, постраничная выдача (`limit`/`page`), фильтр по станции
  метро — ожидается 200 и поле `orders` (список);
- негативный кейс: запрос заказов несуществующего курьера — ожидается 404;
- отдельный тест запроса по двум станциям (`nearestStation`) — ожидается
  200, но фиксирует известный баг бэкенда (см. ниже).

### test_accept_order.py — принятие заказа (`PUT /api/v1/orders/accept/:id?courierId=`)
- успешное принятие заказа (200, `ok: true`);
- запрос без номера заказа в пути — ошибка (см. баг-репорты);
- запрос с несуществующим номером заказа — 404 + текст ошибки;
- запрос с несуществующим ID курьера — 404 + текст ошибки;
- повторное принятие заказа другим курьером — 409 «Этот заказ уже в работе».

### test_get_order_by_number.py — заказ по треку (`GET /api/v1/orders/track?t=`)
- успешный запрос возвращает объект с заказом (200, `track` совпадает);
- запрос без параметра `t` — ошибка (см. баг-репорты);
- запрос с несуществующим трек-номером — ошибка (см. баг-репорты).

## Известные баги, зафиксированные в тестах

### Баги бэкенда

1. **Список заказов: несколько станций (`nearestStation`).** При передаче
   нескольких значений `nearestStation` (множественные query-параметры)
   сервер возвращает `500` с ошибкой `Unexpected token , in JSON at
   position 1`. Поведение подтверждено вручную в Postman. Тест
   `test_order_list_stations_bug` ожидает `200` по контракту и падает,
   фиксируя баг в отчёте Allure (шаг «BUG BACKEND» с анализом ошибки).

### Расхождения документации и фактического поведения API

2. **Путь списка заказов без префикса `/api/`.** В документации указан
   путь `/v1/orders?courierId=...` — без префикса `/api/`. Запрос по этому
   пути возвращает HTML-страницу или `405 Not Allowed`. В тестах
   используется корректный путь `/api/v1/orders`.

3. **Принятие заказа без номера: 404 вместо 400.** Документация обещает
   `400` с сообщением «Недостаточно данных для поиска» при запросе без
   номера заказа. Фактически эндпоинт `/api/v1/orders/accept` без `:id`
   в пути **не существует** — сервер возвращает `404 Not Found`
   (`{"code":404,"message":"Not Found."}`). Поведение подтверждено
   в Postman. Тест приведён в соответствие с реальным поведением стенда.

4. **Удаление курьера: лишняя точка в сообщении об ошибке.** Документация
   для несуществующего ID обещает сообщение «Курьера с таким id нет».
   Сервер возвращает «Курьера с таким id нет**.**» — с точкой на конце.
   Расхождение зафиксировано в описании теста (`allure.description`);
   тест проверяет текст по константе из `data.py`.

5. **Создание курьера: тексты ошибок отличаются от документации.**
   Сообщения о дубликате логина и о недостатке данных отличаются от
   указанных в документации. В тестах используется `==` по константам
   из `data.py`, чтобы падение теста фиксировало расхождение
   (в комментариях отмечено, что альтернатива — `startswith` — сделала бы
   тест зелёным ценой маскировки бага).

## Запуск проекта

1. Клонировать репозиторий и перейти в папку проекта.

2. Создать и активировать виртуальное окружение:

   ```bash
   python -m venv .venv
   .venv\Scripts\activate        # Windows
   source .venv/bin/activate     # Linux/macOS
Установить зависимости:

bash
pip install -r requirements.txt
Запустить тесты:

bash
pytest tests/ -v
Запуск с генерацией отчёта Allure:

bash
pytest tests/ -v --alluredir=allure-results
allure serve allure-results
Для просмотра отчёта нужен установленный Allure CLI (например, через npm install -g allure-commandline).

Дополнительно
Тестовые данные генерируются динамически (фикстура random_courier_payload в conftest.py), поэтому тесты можно запускать многократно без конфликтов по логинам.
Все константы (URL, ожидаемые коды и сообщения, идентификаторы) вынесены в data.py.
Тестовые запросы снабжены шагами Allure и вложениями (детали запроса и ответа), что упрощает разбор падений.
Курьеры, созданные в тестах принятия заказа, не удаляются после теста — для учебного стенда это допустимо. При необходимости можно вынести создание курьера в фикстуру с teardown.
